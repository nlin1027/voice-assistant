hangover report 1:
Core system (built out over several earlier sessions, not the current focus): a Pipecat cascade voice bot (bot/server/bot.py -- Deepgram STT, OpenAI LLM, Cartesia TTS, smallwebrtc transport) that hands off long-running, open-ended objectives to a local Hermes Agent (Nous Research) via the broker/ package -- store.py (SQLite task rows: status, summary, delivered flag), hermes.py (drives a `hermes -z` one-shot subprocess, sandboxed in Docker, working in hermes-tasks/<task_id>/ bind-mounted to /workspace), broker.py (create/run/dispatch orchestration), cli.py (standalone test harness), slots.py (a SlotPool leases one of several pre-provisioned Hermes profiles so concurrent tasks get physically separate containers), and approved_paths.py (a host-directory allowlist mounted read-only or read-write into the container depending on task risk). Every Hermes task is dispatched with a risk tier -- read_only or edit -- which controls both container network access and mount write-permissions (see hangover report 2 for how this tier system also now gates the newer modules/schedule CLI). The bot exposes a single Pipecat tool, run_hermes_task(objective, task_type, risk), using @tool_options(cancel_on_interruption=False) + FunctionCallResultProperties(is_final=False) so dispatch is fire-and-forget: an immediate "started" acknowledgment returns first, then the real result is injected later as a developer-role context message once Hermes finishes. Because broker.dispatch() runs the Hermes call as an independent asyncio task (not tied to Pipecat's pipeline/worker lifecycle), results survive a client disconnecting mid-task -- store.py tracks queued/running/success/failed plus a delivered flag, and on_client_ready sweeps any undelivered finished tasks into the next session's opening greeting.
